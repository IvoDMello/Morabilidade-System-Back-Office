[ ] 4. LIGAR O RODRIGO AO LOGIN (auth_user_id)
    Por ora tudo que sai do chat assina como Rodrigo (FICHA_CORRETOR_PADRAO
    acima). Basta ligar ELE; a separação por corretor fica para depois — quando
    cada um tiver auth_user_id, o responsável da visita passa a valer sozinho,
    sem mexer em código.
    SEM ISSO, TODA VISITA CAI EM PENDÊNCIA em vez de virar envio automático:
    a ficha é documento jurídico e a API exige um corretor identificado
    (nome + CRECI) para assinar. O CRM descobre quem é pelo auth_user_id.

    O QUE É: existem duas listas de pessoas que hoje não se conhecem.
      - whatsapp.corretores  -> "Rodrigo", "Leandro", "Ivo". São só nomes,
                                usados para atribuir contatos e visitas no CRM.
      - public.usuarios      -> os logins de verdade do back-office, com CRECI.
    A coluna auth_user_id é a ponte entre as duas ("o corretor Rodrigo é o
    usuário tal"). Ela está vazia, e é por isso que a ficha não sai.

    Tudo no Supabase Dashboard -> SQL Editor.

    PASSO A) Ver os dois lados e escolher o e-mail do Rodrigo:

      select id, nome, auth_user_id from whatsapp.corretores order by nome;

      select id, nome_completo, email, creci, ativo
      from public.usuarios order by nome_completo;

    Repare na coluna `creci` do segundo resultado: o usuário escolhido precisa
    ter CRECI preenchido (ou ocultar_creci_ficha = true), senão a API recusa a
    ficha e a pendência chega dizendo exatamente isso.

    PASSO B) Ligar (trocar só o e-mail pelo que apareceu acima):

      update whatsapp.corretores c
      set auth_user_id = u.id
      from public.usuarios u
      where lower(c.nome) = 'rodrigo'
        and lower(u.email) = lower('TROCAR_PELO_EMAIL_DO_RODRIGO');

    Esperado: "UPDATE 1". Se vier "UPDATE 0", o e-mail não bateu — volte ao
    passo A e copie exatamente como está lá.

    PASSO C) Conferir que ficou de pé:

      select c.nome, u.nome_completo, u.email, u.creci, u.ativo
      from whatsapp.corretores c
      join public.usuarios u on u.id = c.auth_user_id
      where lower(c.nome) = 'rodrigo';

    Esperado: 1 linha, com creci preenchido e ativo = true.

    E SE O RODRIGO NÃO TIVER LOGIN? Não tem problema: o que importa é que
    FICHA_CORRETOR_PADRAO aponte para um corretor ligado a um usuário COM
    CRECI. Se o login for seu, ligue o "Ivo" (mesmo SQL, trocando o nome) e
    mude FICHA_CORRETOR_PADRAO para Ivo na Vercel.

[!] PARA A MENSAGEM CHEGAR DE VERDADE NO SEU CELULAR
    O app só envia WhatsApp real com WHATSAPP_PROVIDER=cloud-api. Enquanto
    estiver em "mock" (padrão), o envio é simulado: nada sai, nada chega — o
    cron responde certinho mas nenhum celular toca. Conferir na Vercel:
      Settings -> Environment Variables -> WHATSAPP_PROVIDER
    Se não existir ou estiver "mock", o pré-requisito é o onboarding de
    coexistência na Meta (já mapeado no README, seção "Conectando o WhatsApp").
    Ou seja: receber a pendência no 5521971957245 depende de terminar o setup
    da Meta primeiro — não é um passo desta entrega.

COMO O ENVIO DECIDE (para ler a resposta do cron)
--------------------------------------------------
Para cada visita que começa nos próximos 90 minutos, nesta ordem:
  1. texto livre pro CLIENTE      -> só entrega se ele falou com a gente nas
                                     últimas 24h (regra da Meta, não nossa)
  2. template pro CLIENTE          -> a qualquer hora, se o passo 5 estiver feito
  3. pendência pro PLANTÃO         -> mensagem pronta + link, para encaminhar
Cada visita é avisada UMA vez só. Como o gatilho é horário e a janela é de 90
minutos, o aviso sai entre ~30 e ~90 minutos antes da visita.
Quando a ficha não pôde ser gerada, a pendência vem com o motivo exato da API
(ex.: corretor sem CRECI) — é para a ação ser óbvia sem precisar investigar.
