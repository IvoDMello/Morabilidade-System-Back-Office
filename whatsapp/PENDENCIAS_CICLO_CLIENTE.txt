[ ] 3. DEPLOY DA API (Railway) ANTES do CRM
    O CRM passa a chamar POST /clientes/interno/upsert-por-telefone. Se o app
    subir antes da API, a chamada dá 404 -> o upsert devolve null e o lead
    simplesmente não é promovido (sem erro visível). Não quebra, mas a entrega
    fica pela metade até a API subir.

    Lembrete do healthcheck: /health precisa continuar respondendo, senão o
    Railway mantém a versão antiga no ar e a rota nova some sem aviso.


[ ] 4. SMOKE TEST
    [ ] Upsert (não cria nada de verdade se o telefone já existir):
        curl -X POST https://api.morabilidade.com/clientes/interno/upsert-por-telefone \
          -H "X-Internal-Token: $INTERNAL_API_TOKEN" \
          -H "Content-Type: application/json" \
          -d '{"telefone":"5521971957245","nome_completo":"Teste Ciclo"}'
        Resposta traz {"criado": true|false}. Rodar DUAS vezes: a segunda tem
        que voltar criado=false com o mesmo id — é o teste do "não duplica".

    [ ] Promoção pelo painel: abrir um contato com nome real, trocar a categoria
        de "lead" para "cliente" e salvar. Conferir em /clientes do back-office
        que ele apareceu.

    [ ] Rastro do site (precisa de WHATSAPP_PROVIDER=cloud-api para valer com
        mensagem real; no mock dá para simular): mandar uma mensagem contendo
        "(código *MB-00033*)" com um código que EXISTA no catálogo. Conferir na
        ficha do contato que o imóvel apareceu vinculado como "Interesse" e que
        a timeline registrou o vínculo.
        Com um código que NÃO existe, nada deve acontecer — é a consulta ao
        catálogo, não o texto, que decide.

    [ ] Custo: depois de algumas mensagens, conferir o livro-razão:
          select modo, modelo, count(*) as chamadas,
                 sum(input_tokens) as entrada, sum(output_tokens) as saida,
                 sum(cache_read_tokens) as cache_lido
          from whatsapp.agent_runs
          where created_at > now() - interval '1 day'
          group by modo, modelo;

        Como ler: `modo` deve ser 'organizacional' em tudo que veio do webhook.
        `cache_lido` zerado por várias rodadas significa que o prefixo é curto
        demais para cachear (mínimo 1.024 tokens no Sonnet, 4.096 no Haiku) —
        é informação, não defeito: o prompt organizacional é enxuto de propósito.


O QUE MUDA NA PRÁTICA
---------------------
- Lead que chega pelo WhatsApp passa a existir em /clientes — e portanto nos
  relatórios, no matching e na ficha de visita (que antes saía com cliente_id
  nulo justamente para quem tinha visita marcada).
- A promoção é conservadora de propósito: contato cujo nome ainda é o telefone
  formatado NÃO vira cadastro, e campo que um humano preencheu NUNCA é
  sobrescrito por inferência. Nome, em particular, jamais é tocado.
- Custo de IA passa a ser medido e limitado antes de o volume real chegar.
